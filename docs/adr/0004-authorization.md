# ADR-0004: Авторизация — роли из спеки, видимость в SQL

**Status:** Proposed
**Date:** 2026-10-23
**Deciders:** бэкенд
**Supersedes:** ADR-0001, п. 4 — дополняет: «роль проверяется в middleware, владение — в каждом SQL-запросе» + «сервис повторяет проверку роли»

## Context

После BE-03 доступ проверялся в трёх разных местах, и ни одно не было источником правды:

- публичные маршруты — захардкоженная карта `publicRoutes` в `middleware/auth.go` (7 путей); несуществующий путь отвечал `401`, а не `404`, `HEAD /healthz` — `401`;
- роли операций — только текстом в `summary` спеки («lender, KYC verified»);
- владение — запросы заявки, оффера и сделки по `id` искали только по `id`, списки на `sqlc.narg` без фильтра отдавали всё, включая чужие черновики.

Забыть проверку роли в новом хендлере или владельца в новом запросе было легко, а заметить — нечем.

## Decision

1. **Роли и KYC — расширения операции в спеке:** `x-roles: [borrower, lender, admin]`, `x-kyc-required: true`. Публичность — `security: []`. Контракт остаётся единственным источником: фронт видит те же правила.
2. **`middleware.NewAccessRules(doc)`** читает их при старте. Защищённая операция без `x-roles`, неизвестная роль, `x-roles` у публичной операции, `x-kyc-required` у операции для admin — ошибка, сервер не стартует (`TestNewAccessRulesRejectsBadSpec`). Тест на встроенной спеке требует `x-roles` и `403` у каждой из 44 защищённых операций.
3. **`middleware.Authorize`** стоит перед валидатором и находит операцию тем же роутером kin-openapi (`gorillamux`). Порядок: путь не из спеки → дальше (`404` даст валидатор); `security: []` → дальше; нет principal → `401`; роли нет в `x-roles` → `403 FORBIDDEN`; `x-kyc-required` и KYC не `verified` → `403 KYC_NOT_VERIFIED`. Валидатор пропускает multipart-загрузку, поэтому роль загрузки без этого не проверил бы никто.
4. **`Authenticate` — «мягкий»:** валидная сессия → principal (с `KycStatus` из той же строки сессии, `LEFT JOIN organizations`); нет сессии → дальше без principal; сбой БД → `500`. Протухшая cookie не мешает `login`.
5. **CSRF — после `Authorize`**, по правилу найденной операции: не проверяется у публичных (`register`, `login` — DECISIONS п. 1), у безопасных методов и у путей не из спеки.
6. **Видимость — в SQL.** Чтение заявки, оффера, сделки и их списки идут только через `Get*Visible` / `List*Visible` / `Count*Visible` с обязательными `viewer_role` и `viewer_org` (`Principal.ViewerRole()`, `ViewerOrg()`). Правило — `OR`-ветки по ролям в `WHERE`; неизвестная роль и `uuid.Nil` видят ничего. Чужое и несуществующее одинаково дают `pgx.ErrNoRows` → `404`.
7. **Сервис повторяет проверку роли и KYC** — одна строка, защита в глубину от ошибки в `x-roles`: `p.RequireRole(repository.UserRoleBorrower, …)` → `403 FORBIDDEN`, `p.RequireKYCVerified()` → `403 KYC_NOT_VERIFIED` (`internal/service/principal.go`).

## Rejected

- **Strict-middleware oapi-codegen.** Свой тип в каждом из 10 пакетов `<tag>api` (ADR-0003), `operationID` приходит Go-именем, и он не видит запросы, которые валидатор пропустил (multipart).
- **Карта operationId → роли в Go.** Второй источник правды рядом со спекой; расходится молча.
- **Проверка владельца в сервисе по возвращённой строке.** Каждый новый вызов должен помнить о проверке, а списки так не отфильтровать — их пришлось бы читать целиком.

## Consequences

- Новая операция без `x-roles` не проходит тесты, а не открывается всем.
- `publicRoutes` удалён; публичность определяет только `security: []`.
- Один запрос с `OR`-ветками по роли может получить generic plan без индекса по организации. На объёмах демо незаметно; если `EXPLAIN ANALYZE` покажет проблему — запрос делится на три (`…ForBorrower/Lender/Admin`) с выбором в Go.
- `AccessRules` живёт в `internal/http/middleware/`; если разрастётся (`x-rate-limit`), выносится в `internal/http/access`.
