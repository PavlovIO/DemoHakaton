# ADR-0001: Архитектура MVP и контракт фронтенд–бэкенд

**Status:** Proposed
**Date:** 2026-10-13
**Deciders:** вся команда (4 разработчика + менеджер)

## Context

Нужно за этап разработки хакатона (13–31 октября 2026) собрать MVP «Платформы ликвидности»: регистрация юрлиц с KYC, заявки заёмщиков (РФ), офферы кредиторов (не РФ), чат, принятие оффера → сделка, архив, базовая аналитика для админа.

Ограничения:
- **Время:** ~18 дней, включая подготовку демо.
- **Люди:** 4 разработчика, разработка активно идёт через AI-агентов. Значит, нужен жёсткий машиночитаемый контракт, иначе агенты на фронте и бэке разъедутся.
- **Критерии оценки:** работоспособность полного сценария, разделение на слои, базовая безопасность (XSS, CSRF, защита данных), README с API, модульные тесты бизнес-логики.
- **Желание команды:** бэкенд на Go (часть команды осваивает его с нуля).

## Decision

1. **Контракт-first.** Источник правды — `api/openapi.yaml` (OpenAPI 3.0.3, 51 операция). Любое изменение API — сначала PR в этот файл, потом код.
   - Бэкенд: `oapi-codegen` (strict server, `net/http`) генерирует интерфейс сервера и модели. Мы реализуем только методы интерфейса.
   - Фронтенд: `openapi-typescript` + `openapi-fetch` дают типизированный клиент.
   - До готовности бэка фронт работает против мок-сервера Prism (`prism mock api/openapi.yaml`).
2. **Монолит с тремя слоями.**
   - SPA: React + Vite + TypeScript + TanStack Query.
   - REST API на Go, внутри handler → service → repository.
   - PostgreSQL.
   - Никаких микросервисов и брокеров.
3. **Аутентификация:** серверные сессии в cookie (`HttpOnly; Secure; SameSite=Lax`) + double-submit CSRF-токен в заголовке `X-CSRF-Token`. JWT не используем.
4. **Авторизация:** роль (`admin` / `borrower` / `lender`) проверяется в middleware. Владение сущностью проверяется в каждом SQL-запросе репозитория (`WHERE ... AND org_id = $me`). Чужое всегда отдаёт 404.
5. **Чат и уведомления:** REST + polling (`after_id`) раз в 3–5 с. WebSocket — только если останется время.
6. **KYC/AML:**
   - автосверка с реестром: ЕГРЮЛ через DaData для RU, GLEIF по LEI для остальных;
   - rule-based скрининг: санкционные списки, FATF-юрисдикции, порог суммы;
   - финальное решение принимает админ вручную.
7. **Деньги:** `NUMERIC` в БД, строки в JSON, валюта ISO 4217. Float не используется нигде.

## Options Considered

### Бэкенд: Go vs Python (FastAPI)

| Dimension | Go (net/http + pgx + sqlc + oapi-codegen) | Python (FastAPI + SQLAlchemy) |
|---|---|---|
| Complexity | Med: больше бойлерплейта, его закрывают кодген и агенты | Low |
| Team familiarity | Низкая/средняя, часть команды учит с нуля | Высокая |
| Скорость первой версии | Медленнее на 2–3 дня на старте | Быстрее |
| Типобезопасность контракта | Strict server: несоответствие спеке не компилируется | Pydantic, но OpenAPI генерится из кода (code-first) |
| Деплой | Один бинарник, простой Docker-образ | Нормально |

**Pros Go:** строгий контракт на уровне компилятора, команда прокачивает новый язык, предсказуемая конкурентность для транзакции принятия оффера.
**Cons Go:** риск по срокам на старте, меньше «магии» (валидация, миграции, сессии вручную).

**Решение:** Go, с подстраховкой. Если к 17.10 скелет (auth + одна CRUD-сущность + тест) не работает, переходим на FastAPI. Контракт от этого не меняется.

### Аутентификация: cookie-сессия vs JWT в localStorage

| | Cookie-сессия + CSRF | JWT в localStorage |
|---|---|---|
| XSS украдёт токен | Нет (HttpOnly) | Да |
| CSRF | Нужен токен, закрыт double-submit + SameSite | Не актуален |
| Отзыв (блокировка юзера админом) | Тривиально: удалить строки в `sessions` | Нужен blacklist |
| Сложность | Низкая | Низкая |

**Решение:** cookie-сессия. Блокировка пользователя админом есть в требованиях, а с сессиями она бесплатна.

### Чат: polling vs WebSocket

Polling — 2 ручки, работает через любой прокси, тестируется обычными HTTP-тестами. WebSocket даёт лучший UX, но добавляет отдельный протокол, авторизацию соединения и переподключения. Для демо разница незаметна, поэтому **polling**.

### Уведомления админу: брокер (NATS/RabbitMQ) vs таблица в БД

Брокер — лишний сервис в docker-compose плюс неделя на интеграцию. Таблица `notifications`, которая пишется в той же транзакции, что и смена статуса, атомарна и тривиальна. Выбираем **таблицу**.

## Trade-off Analysis

Главный риск — Go с нуля в жёсткий срок. Компенсируем тремя вещами:
- **кодогенерацией** из спеки: роутинг, парсинг, модели не пишем руками;
- **sqlc:** пишем SQL, получаем типизированный Go;
- **агентами**, которые хорошо справляются с бойлерплейтом, когда есть чёткий контракт.

Контракт-first стоит ~1 дня на старте, но убирает главный источник багов в команде из 4 человек с агентами: расхождение фронта и бэка.

Мы сознательно отказываемся от брокера, WebSocket, микросервисов и ML-антифрода. Ни один из них не входит в критерии оценки.

## Consequences

**Становится проще:**
- фронт стартует сразу на моках;
- агентам можно давать задачи вида «реализуй операцию `acceptOffer` по спеке»;
- README с описанием API = ссылка на спеку + Swagger UI.

**Становится сложнее:**
- каждое изменение API требует обновить спеку и перегенерировать код (добавить `make gen` и проверку в CI);
- polling создаёт лишнюю нагрузку (для MVP это неважно).

**Пересмотреть позже:**
- WebSocket для чата;
- брокер, если появятся внешние интеграции;
- ML-скоринг для AML, когда будут данные.

## Структура репозитория

```
api/openapi.yaml            # контракт — источник правды
backend/
  cmd/server/main.go
  internal/
    http/                   # сгенерированный сервер + реализации хендлеров, middleware (auth, csrf, rate limit)
    service/                # бизнес-логика и статусные машины — здесь модульные тесты
    repository/             # sqlc-запросы
    aml/                    # правила скрининга
    registry/               # клиенты DaData / GLEIF
  migrations/               # goose
  queries/                  # *.sql для sqlc
frontend/
  src/api/                  # сгенерированные типы + openapi-fetch клиент
  src/pages/{auth,borrower,lender,admin}/
docs/adr/
docker-compose.yml          # postgres, backend, frontend, (prism для моков)
Makefile                    # gen, migrate, test, run
```

## Статусные машины

```
Organization KYC:  draft ─submit→ under_review ─approve→ verified
                                     └─reject→ rejected ─submit→ under_review

Application:       draft ─submit→ moderation ─approve→ published ─accept offer→ agreed
                                     └─reject→ rejected ─submit→ moderation
                   draft|moderation|rejected|published ─cancel→ cancelled

Offer:             sent ─accept→ accepted
                        ─reject→ rejected   (borrower | another_offer_accepted | application_cancelled)
                        ─withdraw→ withdrawn
```

Переходы реализуются в `service` одной функцией на сущность (таблица разрешённых переходов) и покрываются табличными тестами.
