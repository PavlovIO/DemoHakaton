# Планы задач бэкенда

По файлу на задачу из бэклога (GitHub issues с меткой `backend`, источник — `scripts/issues.yaml`). План — пошаговая инструкция для исполнителя (человека или агента): что уже есть в коде, какие решения приняты, шаги с критерием готовности, тесты.

Перед работой над задачей прочитай её план целиком, затем [DECISIONS.md](DECISIONS.md) — принятые решения по открытым вопросам планов (он главнее плана при расхождении), затем `AGENTS.md` и разделы `backend/README.md`, на которые ссылается план.

## Ветки и PR

Задача, которая использует ещё не влитый код другой задачи, идёт стеком поверх неё. Остальные — от `main`.

```
main
 ├─ DB-SEC · BE-11 шаг 1 (Notifier) · остаток BE-02 (шаг 3 — после мержа BE-03)
 └─ BE-03
     ├─ BE-06 · BE-14 шаг 1 (audit.go)
     └─ BE-04
         ├─ BE-05 ─ BE-13
         ├─ BE-11 шаги 2–4
         └─ BE-07 ─ BE-08 ─┬─ BE-09
                           └─ BE-10
BE-12, BE-15, BE-16 — от main, когда их зависимости влиты
```

1. **Ветка — от ветки задачи, от которой зависишь** (столбец «Зависит от»). Если она уже в `main` или зависимости нет — от `main`. BE-07 идёт от BE-04, а не от BE-05: KYC ему не нужен.
2. **База PR — родительская ветка**, не `main`: тогда в диффе только своя работа.
3. **Мерж снизу вверх.** После мержа родителя дочернюю ветку переносят: `git rebase --onto origin/main <старая вершина родителя>` и `git push --force-with-lease`. Если ветку родителя удалили после мержа, GitHub сам переключит базу PR на `main`. Rebase всё равно нужен, если мерж был squash.
4. **Ветки задач друг в друга не мержат** (`git merge be-03-auth` в `be-04-…`). Нужен код родителя — rebase на него. Разрешение конфликтов внутри merge-коммита потом приходится повторять в каждом PR стека.
5. **Стек не глубже трёх уровней.** Глубже — сначала добиться мержа нижнего PR.
6. **Общий кусок, нужный двум веткам-соседям** (например, интерфейс `aml.Screener` для BE-05 и BE-07), выносится отдельным коммитом в их общего родителя, а не пишется в каждой ветке заново.
7. **Чужая ветка** (автор PR — другой человек) переписывается force-push'ем только по договорённости с автором.

## Общие куски кода

Одну вещь создаёт одна задача, остальные её используют. Если твоя задача пришла раньше владельца — сделай минимальную версию по описанию ниже и отметь это в PR.

| Что | Где | Владелец |
|---|---|---|
| Текущий пользователь `service.Principal{UserID, OrgID, Role, KycStatus}` и `middleware.PrincipalFromContext`; в хендлерах — только `currentPrincipal(ctx)` | `internal/service/principal.go`, `internal/http/middleware/auth.go`, `internal/http/handler/principal.go` | BE-03 создаёт, BE-04 добавляет `KycStatus` и `currentPrincipal` |
| Проверка роли и KYC по `x-roles` / `x-kyc-required` из спеки | `internal/http/middleware/` | BE-04 |
| Запросы «видимое пользователю» (`*Visible` с обязательными `viewer_role`, `viewer_org`) | `backend/queries/*.sql` | BE-04 создаёт `Get/List/Count*Visible` для заявок, офферов, сделок (`SELECT *`, блок видимости); BE-07/08/09 переписывают их под свои колонки и фильтры, блок видимости не меняя |
| `Notifier` — запись в `notifications` внутри транзакции бизнес-события | `internal/service/notifier.go` | BE-11 |
| Запись `audit_log` с IP и User-Agent из `service.ClientMeta` | `internal/service/audit.go` | BE-14 (BE-03 уже пишет `auth.*` своим хелпером) |
| Запись `status_history` при переходе статуса | `internal/service/status_history.go` | BE-07 |
| Формат номеров `ApplicationNumber(n)` → `APP-000123`, `DealNumber(n)` → `DEAL-000045` | `internal/service/applications.go`, `internal/service/deals.go` | BE-07, BE-09 |
| AML-скрининг `aml.Screener`, вызываемый из `submitKyc` и `submitApplication` | `internal/aml/` | BE-13 |

Хендлер достаёт `Principal` из контекста и передаёт в метод сервиса явным аргументом; сервис не читает контекст запроса. Зависимости сервиса — маленькие интерфейсы рядом с ним (образец — `AuthStore` в PR #67), в тестах подставляются фейки.

## Общий критерий готовности любой задачи

Каждый план ссылается на этот список вместо того, чтобы повторять его.

- `make verify` зелёный; если менялись контракт, `backend/queries/` или миграции — ещё `make gen-check`.
- Интеграционные тесты задачи проходят в `make test-all` на свежей БД (`make db-reset`).
- `backend/README.md`: операции задачи отмечены в «Статус реализации», правила доступа и коды ошибок совпадают с кодом.
- Новые переменные окружения — в `.env.example` и `README.md` («Запуск бэкенда»).
- Чекбоксы issue отмечены, PR ссылается на issue (`Closes #N`).

## Как устроен план

- **Что уже есть** — файлы и запросы, на которые опираться; ⚠️ помечены ловушки в существующем коде.
- **Решения** — что уже решено и почему. Пересматривать — только обсудив с командой.
- **Шаги** — по порядку; каждый заканчивается строкой **Готово:** с проверяемым условием. Следующий шаг начинается, когда условие выполнено.
- **Тесты** — конкретные случаи, которые должны существовать.
- **Открытые вопросы** — что решить до или во время работы; ответ записать в план.
