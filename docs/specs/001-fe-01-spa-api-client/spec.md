## Problem Statement

Каркас SPA уже работает против живого бэкенда, но клиент API типизирован только по путям: тип ответа экран указывает руками, и при изменении контракта компилятор этого не заметит. Сгенерированные типы отстают от `api/openapi.yaml` на 93 строки, и это уже сломало сортировку витрины. Деньги форматируются через число с плавающей точкой, ошибки полей с сервера не попадают в формы, справочников на клиенте нет. Без этих вещей FE-03, FE-04 и FE-12 придётся делать на неустойчивой основе.

### Что уже есть (main `84ef669`)

| Пункт issue | Состояние |
|---|---|
| Vite + React + TS, Router, TanStack Query, ESLint | есть |
| Prettier | **нет** |
| Типы через `openapi-typescript` | есть (`npm run gen:api`), но **устарели**; в `make gen` и в CI не входят |
| Клиент `openapi-fetch` | **нет**: свой `request<T>` в `lib/api-client.ts`, тип ответа задаёт вызывающий |

## Goals

- Тип ответа каждого вызова API выводится из контракта. Если поле переименуют в `api/openapi.yaml`, сборка фронта упадёт.
- Сгенерированные типы совпадают с контрактом, и CI проверяет это так же, как `make gen-check` на бэкенде.
- Деньги отображаются без потери точности для любой строки, которую допускает схема `Money`.
- Серверная ошибка валидации подсвечивает конкретные поля формы.
- Справочники стран, валют и способов перевода доступны любому экрану и не запрашиваются повторно в пределах сессии.

## Non-Goals

- Переписывать экраны FE-05…FE-14: они только переходят на новый клиент там, где меняется сигнатура.
- Делать новую дизайн-систему (это FE-02).
- Переходить на `openapi-fetch`. Решение от 2026-10-25: типизируем свой клиент `lib/api-client.ts`, потому что хуки уже на нём.
- Режим работы против Prism-мока и переменная `VITE_API_URL`: бэкенд готов, пункт issue снят.
- Работать офлайн.

## Users and Context

**Основные пользователи:** разработчики фронтенда (команда из 2–3 человек).
**Затронуты:** все пользователи платформы: точность сумм, понятные ошибки.
**Контекст:** каждый новый экран вызывает API через этот клиент.

## User Stories

### Story 1: Типобезопасный вызов API

**As a** разработчик фронтенда
**I want** чтобы тип ответа, параметры пути и query выводились из контракта
**So that** расхождение с бэкендом ловилось при сборке, а не у пользователя

**Acceptance criteria:**

- [ ] **AC-1.1** Given в контракте у операции `getApplication` поле ответа `amount` переименовано When запускается проверка типов фронта Then она падает в каждом месте, где читается `amount`
- [ ] **AC-1.2** Given вызов с параметром пути `{offerId}` When параметр не передан Then код не компилируется
- [ ] **AC-1.3** Given вызов `listApplications` с `sort` вне enum контракта When запускается проверка типов Then она падает
- [ ] **AC-1.4** Given контракт изменён, а типы не перегенерированы When запускается CI Then джоба проверки генерации падает с диффом

### Story 2: Точные деньги

**As a** пользователь
**I want** видеть сумму ровно такой, какой её хранит сервер
**So that** в финансовых документах не было ошибок округления

**Acceptance criteria:**

- [ ] **AC-2.1** Given сумма `"12345678901234567.89"` When она форматируется в RUB Then выводится `12 345 678 901 234 567,89 ₽` без потери копеек
- [ ] **AC-2.2** Given сумма `"0.10"` и валюта `USD` When она форматируется Then выводится `0,10 $`: символ валюты и ровно два знака после запятой
- [ ] **AC-2.3** Given пустая строка, `null` или нечисловая строка When она форматируется Then выводится `—`

### Story 3: Ошибки полей формы

**As a** пользователь, заполняющий форму
**I want** видеть серверную ошибку рядом с полем, к которому она относится
**So that** я понимал, что исправить

**Acceptance criteria:**

- [ ] **AC-3.1** Given сервер ответил 400 `VALIDATION_ERROR` с `details: [{field: "organization.lei", message: "..."}]` When форма обрабатывает ошибку Then сообщение показано под полем LEI, и тост не дублирует его
- [ ] **AC-3.2** Given в `details` есть поле, которого нет в форме When форма обрабатывает ошибку Then сообщение показано общим блоком или тостом
- [ ] **AC-3.3** Given ответ 403, 404 или 409 When ошибка обрабатывается Then пользователь видит сообщение из словаря по `code`, а не `HTTP 409`

### Story 4: Справочники

**As a** разработчик экрана
**I want** получать страны, валюты и способы перевода одним хуком
**So that** не дублировать запросы и списки в коде

**Acceptance criteria:**

- [ ] **AC-4.1** Given справочник стран загружен When его запрашивает второй экран в той же сессии Then новый сетевой запрос не уходит
- [ ] **AC-4.2** Given справочник не загрузился When экран его запрашивает Then экран показывает ошибку загрузки, а не пустой список

## Functional Requirements

### FR-1: Клиент, выводящий типы из контракта

Дорабатываем существующий клиент `lib/api-client.ts` (решение от 2026-10-25), новую библиотеку не подключаем.

**Must:**
- выводить тип тела запроса, параметров пути, query и успешного ответа из `api/openapi.yaml`;
- сохранить текущее поведение: cookie-сессия, `X-CSRF-Token` из cookie `csrf_token` на POST/PUT/PATCH/DELETE, multipart без ручного `Content-Type`, 204 без тела;
- бросать ошибку с `status`, `code` и `details`, сгруппированными по полю.

**Must not:**
- требовать от вызывающего кода указывать тип ответа вручную.

### FR-2: Генерация типов в общем пайплайне

**Must:**
- перегенерировать типы из актуального контракта и починить компиляцию;
- перевести витрину на `sort=published_at_desc` (см. `docs/refactor/frontend.md`, п. 1);
- включить генерацию в `make gen`, а проверку совпадения в CI.

### FR-3: Обработка ошибок

**Must:**
- при 401 вне страниц `/login` и `/register` уводить на вход с возвратом на исходный адрес;
- давать формам способ разложить `details` по полям;
- держать словарь сообщений по всем `code` из контракта.

### FR-4: Форматирование

**Must:**
- форматировать деньги из строки без промежуточного числа с плавающей точкой;
- держать форматирование даты, времени и даты со временем в одном модуле.

### FR-5: Справочники

**Must:**
- дать хуки для `listCountries`, `listCurrencies`, `listTransferMethods` с кэшем на сессию.

### FR-6: Инструменты

**Must:**
- добавить форматтер кода с проверкой в pre-commit и CI.

## Non-Functional Requirements

### Performance

- Справочник запрашивается не больше одного раза за сессию.

### Security

- CSRF-токен берётся только из cookie и не сохраняется ни в каком хранилище браузера.

### Reliability

- Прогон `npm run test:integration` проходит после замены клиента.

## Error Scenarios

| Scenario | Expected Behavior |
|----------|-------------------|
| Ответ не JSON (502 от прокси) | Ошибка с `code: INTERNAL` и HTTP-статусом, тост «Внутренняя ошибка сервиса» |
| 401 на фоновом запросе | Один редирект на `/login`, без цикла |
| 403 `CSRF_INVALID` | Сообщение «Сессия устарела, обновите страницу» |
| 429 `RATE_LIMITED` | Сообщение из словаря, без автоповтора |

## Open Questions

Все вопросы закрыты 2026-10-25:

- Клиент — свой `lib/api-client.ts`, без `openapi-fetch`.
- Режим Prism-мока и `VITE_API_URL` не делаем: бэкенд готов (`make backend-up`). Пункт issue снят.
- Деньги показываем с символом валюты (`₽`, `$`, `€`); если символа нет, выводим ISO-код.
