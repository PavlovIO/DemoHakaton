# Feature 003: FE-03 — регистрация и вход (доработка)

**Status:** Approved

## Problem Statement

Компания регистрируется и входит, но форма расходится с контрактом. Клиент пропускает пароль из 8–9 символов, а сервер требует минимум 10, и пользователь узнаёт об этом только из тоста. Автозаполнения по ИНН / LEI нет, хотя сценарий #1 на него опирается, а мок реестра на бэкенде уже готов (BE-06). Страна вводится свободным текстом, серверные ошибки полей не подсвечиваются. Админа после входа отправляет на `/dashboard`, хотя его кабинет в `/admin`.

### Что уже есть (main `84ef669`)

| Пункт issue | Состояние |
|---|---|
| Выбор роли; заёмщику RU зафиксирован, кредитору RU недоступна | есть |
| Автозаполнение по ИНН / LEI, кнопка «Найти» | **нет** |
| Клиентская валидация по ограничениям спеки | частично; расходится: пароль 8 вместо 10, ИНН не проверяется на 10 цифр, LEI не проверяется на `^[A-Z0-9]{20}$`, нет максимальных длин |
| Серверные ошибки полей | **нет**: только тост |
| Вход, выход | есть |
| Редирект в кабинет по роли | частично: все роли уходят на `from` или `/dashboard` |

## Goals

- Форма отклоняет на клиенте всё, что отклонит `RegisterRequest` в контракте, и ничего сверх этого.
- Пользователь с ИНН (RU) или LEI демо-компании получает название, адрес и рег. номер одной кнопкой.
- После входа каждая роль попадает в свой кабинет.

## Non-Goals

- Восстановление пароля, подтверждение email, капча (`captcha_token` в контракте есть, но капча выключена).
- Приглашение нескольких пользователей в компанию.

## Users and Context

**Основные пользователи:** представитель российской компании-заёмщика, представитель зарубежного кредитора, администратор (только вход).
**Контекст:** первое знакомство с платформой. Ошибка в форме здесь стоит дороже всего.
**Ментальная модель:** «ввёл ИНН — данные подтянулись».

## User Stories

### Story 1: Регистрация заёмщика с автозаполнением

**As a** представитель российской компании
**I want** ввести ИНН и получить данные компании из реестра
**So that** не перепечатывать название и адрес

**Acceptance criteria:**

- [ ] **AC-1.1** Given роль «Заёмщик», введён ИНН демо-компании When пользователь нажимает «Найти» Then поля «Название», «Юридический адрес», «Рег. номер» заполняются из ответа реестра, и их можно править
- [ ] **AC-1.2** Given реестр ответил `found: false` When поиск завершён Then под полем видно «Компания не найдена в реестре, заполните вручную», поля остаются как были
- [ ] **AC-1.3** Given пользователь печатает ИНН When он ещё не нажал «Найти» Then запрос к реестру не уходит (DECISIONS п. 38: поиск по кнопке, не на каждый символ)
- [ ] **AC-1.6** Given поле «Название» заполнено вручную When реестр вернул непустое `name` Then поле перезаписано значением реестра; поле, для которого реестр вернул `null`, не меняется
- [ ] **AC-1.7** Given реестр вернул `registry_status: liquidating` When поиск завершён Then рядом с результатом предупреждение о статусе, регистрация доступна
- [ ] **AC-1.4** Given реестр вернул 429 When поиск завершён Then пользователь видит «Слишком много запросов, попробуйте через минуту», и форма остаётся рабочей
- [ ] **AC-1.5** Given у заёмщика поле страны When форма открыта Then страна равна RU и не меняется

### Story 2: Регистрация кредитора

**As a** представитель зарубежного кредитора
**I want** выбрать страну из списка и найти компанию по LEI
**So that** зарегистрироваться без ошибок в коде страны

**Acceptance criteria:**

- [ ] **AC-2.1** Given роль «Кредитор» When пользователь открывает выбор страны Then в списке есть страны из `listCountries`, кроме RU
- [ ] **AC-2.2** Given введён LEI из 19 символов When форма отправляется Then под полем LEI ошибка формата, и запрос `register` не уходит
- [ ] **AC-2.3** Given введён валидный LEI демо-компании When пользователь нажимает «Найти» Then поля компании заполняются, как в AC-1.1

### Story 3: Валидация и серверные ошибки

**As a** регистрирующийся пользователь
**I want** видеть ошибку у конкретного поля
**So that** сразу понимать, что исправить

**Acceptance criteria:**

- [ ] **AC-3.1** Given пароль из 9 символов When форма отправляется Then под полем пароля «Минимум 10 символов», и запрос не уходит
- [ ] **AC-3.2** Given роль «Заёмщик» и ИНН не из 10 цифр When форма отправляется Then ошибка под полем рег. номера
- [ ] **AC-3.3** Given email уже зарегистрирован When сервер отвечает 409 `CONFLICT` Then текст сервера «Пользователь с таким email уже существует» показан над кнопкой отправки, введённые данные сохранены
- [ ] **AC-3.4** Given сервер вернул 400 с `details` по полю `organization.registration_number` When ответ обработан Then ошибка показана под полем рег. номера

### Story 4: Вход и выход

**As a** зарегистрированный пользователь
**I want** после входа попадать в свой кабинет
**So that** сразу начать работу

**Acceptance criteria:**

- [ ] **AC-4.1** Given админ вводит верные данные When вход выполнен Then открывается кабинет админа
- [ ] **AC-4.2** Given заёмщика выкинуло с `/applications/123` на вход When он вошёл Then открывается `/applications/123`
- [ ] **AC-4.3** Given неверный пароль When вход отправлен Then общим блоком «Неверный email или пароль» без уточнения, какое поле неверно, и без редиректа
- [ ] **AC-4.6** Given аккаунт заблокирован When вход отправлен Then общим блоком «Аккаунт заблокирован»
- [ ] **AC-4.4** Given пользователь в кабинете When он нажимает «Выйти» Then сессия на сервере закрыта, кэш данных очищен, открыта страница входа, и кнопка «Назад» не показывает данные кабинета
- [ ] **AC-4.5** Given пользователь уже вошёл When он открывает `/login` или `/register` Then его перенаправляет в кабинет

## Functional Requirements

### FR-1: Валидация по контракту

**Must:**
- брать ограничения из `RegisterRequest` и `OrganizationCreate`: email до 254 символов, пароль 10–128, название 2–300, адрес до 1000, рег. номер до 50 (для RU — 10 цифр ИНН), LEI `^[A-Z0-9]{20}$`, страна `^[A-Z]{2}$`;
- проверять правило ролей: заёмщик — только RU, кредитор — не RU.

**Must not:**
- требовать на входе больше, чем требует сервер (сейчас на входе минимум 6 символов пароля — это ни на что не влияет, но расходится с регистрацией).

### FR-2: Автозаполнение

**Must:**
- вызывать `registryLookup` по кнопке «Найти» с `country_code` и номером (ИНН для RU, LEI для остальных);
- заполнять из ответа `name`, `legal_address`, `registration_number`, перезаписывая поля непустыми значениями реестра и не блокируя ручную правку;
- показывать предупреждение, если `registry_status` не `active`;
- показывать, что данные из реестра. В MVP `source: mock`.

**Must not:**
- запускать поиск автоматически на ввод.

### FR-3: Редирект по роли

**Must:**
- после входа или регистрации уводить на исходный адрес, если он принадлежит роли пользователя, иначе в кабинет роли.

## Non-Functional Requirements

### Performance

- Не больше одного запроса к реестру на нажатие «Найти»; повторное нажатие во время запроса игнорируется.

### Security

- Пароль не попадает в логи, адресную строку и хранилище браузера.
- Сообщение о неверном входе не раскрывает, существует ли такой email.

### Reliability

- Если реестр недоступен (502), регистрация проходит вручную.

## Error Scenarios

| Scenario | Expected Behavior |
|----------|-------------------|
| Реестр 502 | «Реестр временно недоступен, заполните данные вручную» |
| Реестр 429 | Сообщение о лимите, кнопка «Найти» снова активна через 60 с |
| `register` 429 (10 регистраций с IP в час) | Сообщение о лимите, данные формы не теряются |
| `login` 429 | Сообщение о лимите попыток |
| Справочник стран не загрузился | Сообщение об ошибке и «Повторить»; у заёмщика RU работает без справочника |

## Open Questions

Все вопросы закрыты 2026-10-25 (ответы бэкенда сверены с `backend/internal/service/auth`):

- Занятый email и занятый рег. номер — 409 `CONFLICT` без `details`, различаются только текстом сообщения. Показываем текст сервера общим блоком над кнопкой отправки, к полю не привязываем.
- Неверный email или пароль — 401 «Неверный email или пароль», показываем общим блоком. Заблокированный аккаунт — 403 «Аккаунт заблокирован».
- Ошибки валидации (роль, страна, длина пароля) приходят 400 с `details` по полю и показываются у поля (AC-3.4).
- «Найти» перезаписывает поля значениями из реестра: пользователь нажал кнопку сам, а поля потом можно поправить. Перезаписываются только поля, которые реестр вернул непустыми.
- `registry_status`, отличный от `active`, показываем предупреждением рядом с результатом поиска. Регистрацию не блокируем: решение о такой компании принимает админ при KYC.
