# Feature 005: FE-12 — админ: верификация компаний (доработка)

**Status:** Approved
**Created:** 2026-10-25
**Branch:** `005-fe-12-admin-kyc`
**Issue:** #44 · **Сценарий:** #3 · **Зависит от:** FE-02 (маршрут `/admin/organizations`, таблица, фильтры, модалка с причиной); BE: фильтр `organization_id` в `adminListAuditLog` (только для блока «История»)

---

## Problem Statement

Админ видит очередь `under_review` и может одобрить или отклонить компанию, но решает вслепую: в списке только название, страна и рег. номер. Документы, бенефициары, результат сверки с реестром и AML-флаги бэкенд отдаёт в `adminGetOrganization`, но фронт их не показывает. Списка всех компаний с поиском нет. Причина отказа вводится через `prompt()`. Если одобрение заблокировано AML-флагом (409 `CONFLICT`), админ видит общее «данные уже изменились».

### Что уже есть (main `84ef669`)

| Пункт issue | Состояние |
|---|---|
| Очередь «на проверке» | есть, вкладка в `AdminPanel`, догрузка страниц |
| Все компании с фильтрами и поиском | **нет** |
| Карточка: профиль, бенефициары, документы, сверка с реестром, AML-флаги, история | **нет**; история — из журнала аудита (решение от 2026-10-25) |
| Одобрить | есть, из списка, без карточки |
| Отклонить с обязательной причиной | частично: `prompt()`, пустая причина отменяет действие |
| Сообщение о блокировке AML-флагом | **нет**: общий текст для `CONFLICT` |

## Goals

- Админ принимает решение по компании на одном экране, не открывая БД и другие разделы.
- Расхождения между введёнными данными и реестром видны без ручного сравнения.
- Причина блокировки одобрения понятна из сообщения.

## Non-Goals

- Разбор AML-флагов (resolve) — это FE-13 (закрыт). Здесь флаги только показываются со ссылкой на раздел AML.
- Редактирование данных компании админом.

## Users and Context

**Основной пользователь:** администратор платформы.
**Контекст:** разбор очереди верификации, несколько компаний в день; решение юридически значимо и попадает в аудит.
**Ментальная модель:** «досье компании»: всё, что прислали, рядом с тем, что сказал реестр.

## User Stories

### Story 1: Список компаний

**As a** администратор
**I want** видеть очередь на проверке и искать среди всех компаний
**So that** быстро находить нужную

**Acceptance criteria:**

- [ ] **AC-1.1** Given админ открывает раздел компаний When экран загружен Then по умолчанию показан фильтр `kyc_status=under_review` и счётчик компаний
- [ ] **AC-1.2** Given админ вводит в поиск часть названия или рег. номера When поиск применён Then список содержит только совпадения (`q`), а фильтр сохраняется в адресе
- [ ] **AC-1.3** Given выбраны фильтры статуса, типа и страны When админ обновляет страницу Then фильтры и результаты те же
- [ ] **AC-1.4** Given по фильтру ничего нет When список загружен Then показано пустое состояние с кнопкой сброса фильтров

### Story 2: Карточка компании

**As a** администратор
**I want** видеть профиль, бенефициаров, документы, сверку с реестром и AML-флаги
**So that** принять обоснованное решение

**Acceptance criteria:**

- [ ] **AC-2.1** Given компания в `under_review` When админ открывает карточку Then видны профиль, бенефициары с долями, документы, пользователи компании, AML-флаги и результат сверки с реестром
- [ ] **AC-2.2** Given название в профиле отличается от `registry_check.name` When карточка открыта Then поле выделено, и рядом показаны оба значения
- [ ] **AC-2.3** Given `registry_check` равен `null` или `found: false` When карточка открыта Then вместо сверки — явное «Компания не найдена в реестре» или «Сверка не проводилась»
- [ ] **AC-2.4** Given документ в карточке When админ нажимает на него Then файл скачивается
- [ ] **AC-2.5** Given открытый AML-флаг с severity `high` When карточка открыта Then флаг выделен, и есть ссылка на раздел AML
- [ ] **AC-2.6** Given компания зарегистрировалась, загрузила документы, отправила KYC, её пользователь создал заявку When админ открывает блок «История» Then видны все эти события по убыванию времени: действие, автор, время
- [ ] **AC-2.7** Given в истории событие действия админа над компанией (например, прошлый отказ KYC) When история показана Then событие есть в ленте, и видно, что автор — админ
- [ ] **AC-2.8** Given событий больше одной страницы When админ нажимает «Показать ещё» Then догружаются более ранние события без дублей и без нарушения порядка

### Story 3: Решение

**As a** администратор
**I want** одобрить или отклонить компанию с причиной
**So that** компания получила результат и знала, что исправить

**Acceptance criteria:**

- [ ] **AC-3.1** Given админ нажал «Отклонить» When открылась модалка Then кнопка подтверждения неактивна, пока причина пуста или состоит из пробелов
- [ ] **AC-3.2** Given причина введена When админ подтверждает Then компания уходит в `rejected`, исчезает из очереди, карточка показывает новый статус
- [ ] **AC-3.3** Given у компании открытый флаг `high` When админ нажимает «Одобрить» Then показано «Одобрение заблокировано открытым AML-флагом высокого риска» со ссылкой на флаг, статус не меняется
- [ ] **AC-3.4** Given компания уже не в `under_review` (решение принял другой админ) When админ нажимает любое решение Then показано «Статус компании изменился», и карточка перезагружается
- [ ] **AC-3.5** Given компания не в `under_review` When карточка открыта Then кнопок решения нет

## Functional Requirements

### FR-1: Список

**Must:**
- использовать `adminListOrganizations` с фильтрами `kyc_status[]`, `type`, `country_code`, `q` и страничной догрузкой;
- держать фильтры в query-строке.

### FR-2: Карточка

**Must:**
- показывать всё, что отдаёт `adminGetOrganization` (`OrganizationDetails`): профиль, бенефициары, `documents`, `aml_flags`, `users`, `registry_check`;
- сравнивать название, адрес и рег. номер с `registry_check` и выделять расхождения;
- скачивать документы через `downloadDocument`.

### FR-2a: История взаимодействия компании с платформой

Решение от 2026-10-25: история компании — это её действия на платформе из журнала аудита.

**Must:**
- показывать единой лентой (новые сверху) события журнала двух видов: действия над самой компанией (в том числе решения админов) и действия пользователей компании. Ленту отдаёт `adminListAuditLog` с новым фильтром `organization_id` (BE-задача, см. «Зависит от»);
- для каждого события показывать действие понятной подписью, автора, время;
- догружать ленту постранично.

**Must not:**
- показывать одно событие дважды, если оно попадает под оба вида фильтра.

### FR-3: Решения

**Must:**
- одобрять через `adminApproveKyc` после модалки подтверждения с необязательным комментарием (`AdminComment`);
- показывать флаги `medium` / `low` без блокировки одобрения;
- отклонять через `adminRejectKyc` с обязательной причиной в модалке;
- различать 409 `CONFLICT` (AML-блокировка) и 409 `INVALID_STATUS_TRANSITION`.

**Must not:**
- использовать системные диалоги браузера.

## Non-Functional Requirements

### Performance

- Карточка открывается одним запросом `adminGetOrganization`, без N+1 по документам и флагам.

### Security

- Экран и запросы доступны только роли `admin` (guard + 403 бэкенда).

### Reliability

- Двойной клик по «Одобрить» не отправляет два запроса.

## Error Scenarios

| Scenario | Expected Behavior |
|----------|-------------------|
| 409 `CONFLICT` при approve | Сообщение про AML-флаг, ссылка на флаг |
| 409 `INVALID_STATUS_TRANSITION` | «Статус изменился», перезагрузка карточки |
| 404 карточки | Экран «Компания не найдена», ссылка в список |
| Документ не скачался | Тост с ошибкой, карточка остаётся открытой |

## Open Questions

Все вопросы закрыты 2026-10-25:

- История компании — события журнала аудита (FR-2a). Бэкенд добавляет в `adminListAuditLog` фильтр `organization_id`: действия над компанией и действия её пользователей одной лентой с серверной пагинацией. Это отдельная BE-задача и зависимость этой спеки; фронт склеивать ленты не будет.
- При одобрении — необязательное поле комментария (`AdminComment`) в модалке подтверждения.
- Одобрение блокируют только открытые флаги `high` (так в контракте). Флаги `medium` и `low` показываются в карточке как информация.

## Out of Scope (Future Considerations)

- Массовые решения по нескольким компаниям.
- Назначение компании конкретному проверяющему.
