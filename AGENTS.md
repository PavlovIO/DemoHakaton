# AGENTS.md

MVP платформы ликвидности: SPA (React + Vite + TypeScript + TanStack Query) → REST API на Go → PostgreSQL. Решения зафиксированы в `docs/adr/`.

Проект оценивают по ТЗ. Каждое изменение должно сохранять:
1. **Работоспособность** — функции MVP работают без критических ошибок; `make verify` зелёный.
2. **Слои** — Frontend / Backend / DB разделены, код структурирован (см. «Структура»).
3. **Безопасность** — защита от XSS и CSRF, данные пользователей защищены (см. «Безопасность»).
4. **Документацию** — README с локальным развёртыванием и описанием API актуален (см. «Документация»).

## Структура

Монорепо: контракт OpenAPI (`api/`), бэкенд на Go (`backend/`, модуль Go — именно там, не в корне), фронтенд (`frontend/`, ещё не создан). Команды — через `Makefile` из корня репо.

Контракт-first (`docs/adr/0001-architecture-and-api-contract.md`): любое изменение API начинается с `api/`, потом код бэка и фронта.
- Источник правды — `api/openapi.root.yaml` + `api/paths/*.yaml` (по файлу на тег) + `api/schemas/*.yaml`. `api/openapi.yaml` — сгенерированный бандл.
- Слои бэкенда: `internal/http/handler` (транспорт, по файлу на тег) → `internal/service` (бизнес-логика, статусные машины, транзакции) → `internal/repository` (sqlc). Каждый слой знает только о соседнем снизу: хендлер не ходит в репозиторий, сервис не знает про HTTP.
- SQL-запросы пишутся в `backend/queries/*.sql`, схема БД — в `backend/migrations/` (goose).
- `internal/aml` — правила AML-скрининга, `internal/registry` — клиенты DaData/GLEIF, `internal/apperr` — доменные ошибки.
- Новая операция API — по шагам из раздела «Как добавить операцию» в `backend/README.md`; образец — справочники (`handler/dictionaries.go`, `service/dictionaries.go`).

Сгенерированное — руками не править, а перегенерировать:

| Изменил | Запусти | Обновится |
|---|---|---|
| `api/**/*.yaml` | `make gen-api` | `api/openapi.yaml`, `backend/internal/openapi/openapi.yaml`, `backend/internal/http/api/**/*.gen.go` |
| `backend/queries/*.sql` или миграции | `make gen-sqlc` (нужен Docker) | `backend/internal/repository/sqlc/` |

Сгенерированные файлы коммитятся; CI (`make gen-check`) падает, если они не совпадают с источниками. После правки контракта прогони `make lint-api` и `make diff-api` (ломающие изменения).

- Новый тег API: скопируй `gen.go` и `register.go` из `internal/http/api/authapi/`, замени имя пакета и `-include-tags`, реализацию положи в `internal/http/handler/<tag>.go` (`docs/adr/0003-server-package-per-tag.md`).
- Новая миграция — `make migrate-create name=<name>`; менять уже существующие миграции — сначала спроси.
- Перед изменением схемы БД прочитай `docs/db/schema.md`.

## Безопасность

Схема аутентификации описана в `api/openapi.root.yaml` (`info.description`) и `backend/README.md` («Аутентификация», «Роли и доступ») — не меняй её без обсуждения.
- **CSRF:** сессия — HttpOnly-cookie `session`; все запросы, кроме GET/HEAD/OPTIONS, обязаны слать `X-CSRF-Token`, равный cookie `csrf_token` (double-submit), иначе `403 CSRF_INVALID`. Не делай исключений для мутирующих эндпоинтов и не меняй состояние в GET.
- **Доступ (IDOR):** владение проверяется в каждом запросе к сущности — в SQL всегда `AND org_id = <организация пользователя>`. Чужая сущность → `404`, не `403`. Роль (`borrower`/`lender`/`admin`) проверяй в сервисе, а не только на фронте.
- **SQL:** только параметризованные запросы через sqlc (`backend/queries/`); никакой склейки SQL из строк.
- **Входные данные:** ограничения (`maxLength`, `format`, `enum`, `minimum`) задаются в схемах контракта — их проверяет `handler/validate.go`; не дублируй валидацию вручную в хендлере.
- **Пароли и токены:** хэширование — только `internal/service/password.go` (argon2id); в БД — только хэши токенов сессий. Пароли, токены, хэши и содержимое документов не логируй и не возвращай в ответах.
- **XSS (фронт):** пользовательский текст (чат, описания заявок, названия компаний) выводи только через JSX-экранирование; `dangerouslySetInnerHTML` с пользовательскими данными запрещён. Токены не клади в `localStorage` — сессия живёт в HttpOnly-cookie, фронт читает лишь `csrf_token` и кладёт его в заголовок.
- 🚫 Не коммить `.env` и реальные секреты; новые переменные окружения добавляй в `.env.example`.

## Фронтенд

- SPA с адаптивной вёрсткой: должна работать на ПК и планшете (ширина от 768px); проверяй оба размера.
- Типы и клиент API — из `api/openapi.yaml`, не описывай DTO руками. До готовности эндпоинта работай против мока `prism mock api/openapi.yaml`.

## Тесты

- Бизнес-логика (`internal/service`, `internal/aml`) — обязательно модульные тесты; статусные переходы — табличными тестами (одна функция переходов на сущность, ADR-0001).
- Тесты хендлеров — через `httptest` с настоящим роутером и фейковым сервисом (образец: `handler/dictionaries_test.go`).
- Интеграционные тесты с БД пропускаются при `testing.Short()` или без `DATABASE_URL` (образец: `service/dictionaries_integration_test.go`).

```bash
make test       # юнит-тесты, БД не нужна
make test-all   # + интеграционные (сначала make db)
go -C backend test -short -run TestName ./internal/service/   # один тест
```

- Изменил шаги запуска, переменные окружения, зависимости от Docker/инструментов → обнови `README.md` («Запуск бэкенда») и `.env.example`.

## Коммиты: Conventional Commits

Формат: `<type>(<scope>): <описание>`. Описание — в повелительном или назывном стиле, без точки в конце, до ~72 символов.

- Типы: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `build`, `ci`, `chore`. Не используй нестандартные типы (`db: ...`) — пиши `feat(db): ...`, `fix(db): ...`.
- Scope — затронутая область: `http`, `db`, `api`, `backend`, `frontend`, `ci` или id задачи (`be-02`). Если затронуто много областей — scope можно опустить.
- Ломающее изменение (контракт API, схема БД): `feat(api)!: ...` и строка `BREAKING CHANGE: <что сломалось>` в теле.
- Один коммит — одно логическое изменение; не смешивай рефакторинг и новую функциональность.
- Тело (необязательно) — *почему* сделано изменение, а не пересказ диффа.

Примеры из истории:
```
feat(be-02): argon2id password hashing and TxManager
fix(http): paramName — типизированный nil, Unwrap() []error
refactor(http): сгенерированный сервер — пакет на тег
```

## Код: clean code

Форматирование и стиль проверяют `gofmt` и `golangci-lint` (`backend/.golangci.yml`, запускаются хуками lefthook) — не дублируй их правила, просто прогоняй линтер.

Сверх линтера:
- Имена говорят о намерении: `pendingOffers`, не `list2`/`tmp`/`data`. Без невнятных сокращений, кроме идиоматичных для Go (`ctx`, `err`, `tx`).
- Функция делает одно дело. Если её приходится описывать через «и» — раздели.
- Ранний возврат вместо вложенных `if`/`else`; «счастливый путь» — без отступа.
- Без магических чисел и строк — именованные константы.
- Не дублируй логику: при втором повторе вынеси в общую функцию, но не строй абстракции «на будущее».
- Ошибки не глотай: оборачивай с контекстом (`fmt.Errorf("create offer: %w", err)`) или возвращай `apperr`; HTTP-статус выбирает только `handler/errors.go`.
- Меняешь код — оставь его чище, чем было, но в рамках задачи: крупный рефакторинг — отдельным коммитом `refactor(...)`.

Комментарии (требование ТЗ):
- Doc-комментарий у каждого пакета и экспортируемого типа/функции.
- Ключевые блоки логики — статусные переходы, проверки доступа, расчёты денег и процентов, AML-правила, транзакции — комментируй: *почему* так и какой инвариант держится. Очевидный код не пересказывай.
- Закомментированный код и отладочный вывод удаляй.
